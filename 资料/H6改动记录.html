改动 1：给时序参数起"用途名"

问题是什么

MCU 给霍尔芯片下命令，靠的是"把 SCK 拉高并保持一段时间"（动画网页第 4、5 关）。代码里这些时长用手册里的编号命名，比如 TD4_DELAY_US、TD7_DELAY_US。麻烦在于，同一个编号在两代芯片的手册里代表不同的命令：

宏名H5 手册里是H6 手册里是代码拿它来干什么
TD4写寄存器，24us写 LED 亮度，18us写寄存器
TD7频率校准，128us让芯片休眠，28us频率校准
TD10校准后等待，>2us频率校准，128us校准后等待

button.h 里早就有人按 H6 手册写好了一组 TD 宏，但函数里用的还是 H5 的编号。如果直接把型号开关改成 6，写寄存器会变成写 LED，上电校准会变成让芯片休眠。编译不报任何错，板子上就是什么都读不对，而且很难查到原因。

为什么这样改

函数只说"我要干什么"，具体用哪个 TD 交给宏去选。现在 Hall_write_register() 里写的是"写寄存器用的时长"（HALL_TD_WR_REG），型号是 5 时它自动对应 H5 的 TD4（24us），型号改成 6 时自动对应 H6 的 TD6（39us）。以后切换芯片只改一个开关，函数一行都不用动，也就不会再踩编号的坑。
H6 的三个"等待"值比手册要求多留了余量。手册对等待只要求"不少于"（>4us、>3us、>50us），多等几微秒没有坏处。而代码里的延时其实比写的数短：DELAY_OUT(x) 先减 1，CT16B1_DelayUs() 内部再少数 2，定时器实际只计了大约 x−3 微秒（动画网页第 7 关）。所以等待类干脆给足：8、10、60。"按住"类（±5%）不能这样做，多了少了都会被芯片认成别的命令，这几个还是用原来的宏，靠逻辑分析仪实测来确认。
#else 分支一字不差地对应原来的宏。型号是 5 时，新名字展开后和改之前完全一样。这正是能"证明没改坏"的前提，见下一节。

怎么证明没改坏

型号仍是 5，新宏展开后和原来一模一样，所以编译出来的固件应当逐字节相同。Codex 在 Keil 里改前改后各编译一次，用 fc /b 比较两份 Sample.hex，结果是"找不到差异"。

这样就不需要上板测试：重构（换写法）用"hex 相同"来证明，改行为（换芯片）留到下一步再上板。两件事分开做，出问题时才分得清是哪一件出了错。

改动 2：注释改成英文

第 1 步提交后，button.h 新加的中文注释在 VS Code 里显示成乱码。原因是：button.h 原本是纯英文文件，我给 Codex 的代码里带了中文注释，Codex 按 GBK 编码存了进去，而 VS Code 按 UTF-8 打开。

修法是把注释换成英文，文件恢复成纯英文，用什么编码打开都不会乱。Codex 顺手把 button.c 里仅有的两行 GBK 中文注释也换成了英文，所以 button.c 现在也是纯英文了，以后不会再有编码问题。

自测：能回答这三个问题，第 1 步就算真的懂了

  1. 为什么只把 USE_HALL_SENSOR 改成 6、而不改函数里的宏名，编译不会报错，板子却会出问题？
    参考答案H6 那组 TD 宏全都存在，编译器只检查名字有没有定义，不知道 TD4 在 H6 里代表"写 LED"。所以能编过，但写寄存器时发出的是 18us 脉冲，芯片把它当成写 LED 的命令。
  2. 为什么这一步改完，hex 文件必须和改之前完全一样？
    参考答案型号仍是 5，新宏在 #else 分支里展开成原来的宏，编译器看到的代码和以前一字不差，生成的机器码自然也一样。如果不一样，就说明除了换名字之外还改到了别的东西。
  3. 为什么等待时间可以多留余量，"按住"的时间却不行？
    参考答案等待在手册里只规定了下限（大于多少），多等只是慢一点。按住的时间是命令本身，芯片按长度判断是哪条命令，只允许 ±5% 的误差，多了少了都会被认成别的命令或不认。
