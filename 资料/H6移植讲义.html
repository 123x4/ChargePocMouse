0. 先看这里：这件事到底要干什么

一句话：MCU 不换，按键算法不换，只换"MCU 和霍尔芯片说话的方式"。

鼠标的左右键下面各有一块磁铁，按下去磁铁靠近霍尔芯片，芯片读到的数值随之变化，代码根据数值判断有没有按下。H5 和 H6 是同一家公司的两代霍尔芯片，封装和引脚一样，但"说话的规矩"变了：命令的格式、校验方法、寄存器地址都不同。所以要改的只是最底层的驱动，集中在两个文件：

  • EM_HapticMouse/inc/button.h：时序参数、芯片型号开关
  • EM_HapticMouse/app/button.c：校准、读写寄存器、初始化表

上层的按键算法（src/my_misc.c）不用重写，最后只需要根据实测数值调几个阈值。

贯穿全程的三条规则

  1. 一次只改一件事，改完马上验证。时序错、校验错、寄存器错，在板子上的现象都是"读出来不对"。全改完再烧录，你就分不清是哪一处错了。
  2. 通过标准必须是具体数值。"看起来正常"不算通过，"读回 0xAA"才算。
  3. 每通过一步就提交一次，并填第 6 节的记录表。出了问题可以退回上一个确定正常的版本。

1. 名词扫盲

名词是什么在这个项目里
datasheet
芯片手册		芯片厂家写的说明书：引脚怎么接、电压多少、命令怎么发、每个寄存器管什么。写驱动时它是唯一的权威，别人的代码只能当参考。资料/GTRY164 ... V1.9 ...pdf（H6）
资料/GTRY154 ...pdf（H5）
寄存器芯片内部的一个个"设置格子"，每个格子有地址（如 0x33）和 8 位的值。往格子里写值就是给芯片下设置，读格子就是查设置。比如 H6 的 0x33 管"连续采样还是单次采样"，0x0B 管放大倍数。
SPI一种芯片之间的通信方式，三根线：时钟 SCK（MCU 打拍子）、MOSI（MCU→芯片）、MISO（芯片→MCU）。每打一拍传 1 位。SCK = PIO1_15（MCU 第 28 脚）
MOSI = PIO0_21（第 12 脚）
MISO = PIO0_22（第 20 脚）
用的是 MCU 的 SSP1 外设，2MHz。
菊花链多颗芯片串成一串：MCU → 芯片 1 → 芯片 2 → MCU。每颗芯片吐出 16 位，两颗就是 32 位（4 字节）。MOSI → 左键芯片 H1 → 右键芯片 H2 → MISO。
所以读回的 4 字节里，前 2 字节是右键，后 2 字节是左键（离 MCU 近的先出来）。
片选常规 SPI 还有一根"片选线"，用来告诉芯片"现在开始说话"。这块板子没有片选线。所以才需要下面的 TD 时间。
TD 时间没有片选线，MCU 就用"把 SCK 拉高一段特定时长"来下命令。拉高 5us 是"读数据"，39us 是"执行读/写寄存器"，128us 是"频率校准"……时长不同，命令就不同。允许误差只有 ±5%。代码在 Hall_CLK_Command_SET() 里：先把 PIO1_15 从 SPI 功能切成普通 IO，拉高 N 微秒，拉低，再切回 SPI。
同事说"TD 时间要自己量"指的就是这个。
CRC / 校验位数据里额外带的几位，用来检查传输有没有出错。收到后按同样的公式再算一遍，结果对不上就说明数据坏了。读采样：16 位里最高 2 位是校验位。
写寄存器：bit14 是校验位，算错了芯片直接丢弃这次写入，而且不报错。
原始值 raw芯片直接给出的测量结果，14 位，范围 0–16383。没有磁场时约为 8192。磁铁靠近，数值往一边偏。按键算法就是看这个偏移量。
示波器 / 逻辑分析仪能把引脚上的电压画成波形的仪器，可以直接量出一个脉冲有多宽。探头接 SCK（PIO1_15），量 5us、39us、128us 那几个脉冲。没有也行，见第 5 节"没有示波器时怎么验证"。
断点 / Watch 窗口Keil 在线调试的功能：程序跑到某一行停下来，然后查看变量的值。本讲义用一个全局变量 g_hall_dbg 存放调试结果，在 Watch 窗口里看。

3. H5 和 H6 到底哪里不一样

项目H5（GTRY154）H6（GTRY164）要改吗
读采样命令（td1）5us5us不用
读采样后的等待>2us>4us（连续模式）要改（留余量）
读/写寄存器命令td4 = 24ustd6 = 39us要改
频率校准命令td7 = 128us，之后等 >2ustd10 = 128us，之后等 td12 > 50us要改
校准时 SDI 的内容无要求（现有代码发 0x55）必须全 0要改
写寄存器校验位只算 8 位数据6 位地址 + 8 位数据要改
寄存器表0x0A–0x270x05–0x35，地址和含义全变了整表重写
连续采样开关0x18 的 bit20x33 的 bit7，默认关（单次）要改
放大倍数0x14 + 0x16，8x–128x0x09 bit5 + 0x0B + 0x29 + 0x2A 四个联动，16/24/48/96x要改
输入高电平门限0.5×VDD0.8×VDD不用（板上 VDD = 3.3V，门限 2.64V，MCU 输出 3.3V 满足）
读采样的数据格式和校验完全相同（14 位数据 + 2 位交错奇偶校验）不用
最大的坑：TD 编号在两代芯片里含义不同 现有代码按编号使用宏：写寄存器用 TD4_DELAY_US，频率校准用 TD7_DELAY_US。H5 里这两个确实是 24us 和 128us。但 button.h 里预留的 H6 那组宏是按 H6 手册编号的：TD4 = 18us（写 PWM）、TD7 = 28us（休眠）。
所以只把 USE_HALL_SENSOR 从 5 改成 6，结果会是：写寄存器变成写 PWM，上电校准变成让芯片休眠。编译不报任何错，板子上就是"什么都读不对"。第 1 步专门处理这个问题。
现有代码里顺手要修的问题
  • Hall_ReadReg() 把 0x55 写进了 hall_spi_rx（接收缓冲区），本意是写 hall_spi_tx（发送缓冲区）。读寄存器时数据位本来就是"任意值"，所以这个错不影响功能，但要改掉。
  • Hall_osc_calibrate() 固定跑 30 次，不检查读回值，所以校准失败了也不知道。
  • 初始化表写完不回读核对，写错了也不知道。
  • USB 挂起再唤醒后不会重新初始化霍尔（suspend.c、usbhw.c）。H5 上一直这样，H6 上要实测一下有没有问题。

4. 动手前的准备

4.1 工具

  • Keil MDK：工程文件是 EM_HapticMouse/Sample.uvprojx，编译和烧录都要用它。VS Code 只能看代码、改代码。先确认你的电脑能打开工程、能编译通过、能烧进板子。如果还没装，或者需要授权，先问同事。
  • 仿真器（J-Link、ULINK 之类）：接板子上的 SWD 调试口，原理图上标的是 "JTAG Program Interface"，引脚是 3V3、SWDIO、SWCLK、nRESET、GND。
  • 示波器或逻辑分析仪：可选。有的话第 2 步更踏实，采样率要 ≥ 20MHz。

4.2 文件编码：VS Code 用户必看

button.c 是 GBK 编码，不是 UTF-8 VS Code 默认按 UTF-8 打开，里面的中文注释会显示成乱码。如果你在乱码状态下直接保存，中文注释就被永久破坏了，还会在 git 里产生一大片无关的改动。
处理方法：在 VS Code 右下角状态栏点 "UTF-8" → "通过编码重新打开" → 选 "Simplified Chinese (GBK)"。确认中文显示正常之后再编辑，保存时也会按 GBK 保存。button.h、my_misc.c 是纯英文，没有这个问题。

4.3 怎么看调试数据：先了解一个坑

Keil 在线调试会在 PAW3950_Init() 之后断开 原理图上，SWD 的时钟脚 SWCLK（PIO0_10）同时接到了光学传感器 PAW3950 的 SPI 时钟上。PAW3950_Init() 一执行（src/PAW3950.c 第 298–299 行），就把这个脚改成了 SPI 时钟，仿真器随即失去连接。

霍尔初始化发生在这之前，所以有两种情况：

  • 只看初始化结果（第 2–4 步）：在 device.c 的 HallSensor_INIT();（约第 462 行）下一行打断点，停下后在 Watch 窗口看 g_hall_dbg。这种情况不受影响。
  • 要看运行中的数据（第 5–6 步）：临时把 PAW3950.c 里切换 SWCLK 的那两行注释掉： 
    //	LPC_IOCON->SWCLK_PIO0_10	&= ~0x07 ;
//	LPC_IOCON->SWCLK_PIO0_10	|= 0x02 ;
    这样光学传感器读不到 ID，PAW3950_Init() 会直接返回 -1，不会卡死，仿真器也能一直保持连接。代价是调试期间鼠标不能移动。在 Watch 窗口右键勾选 "Periodic Window Update"，变量就会实时刷新。调完一定要改回来。

另一条路是 USB 打印：工程里 InfoLog() 走的是 USB，my_misc.c 已经每 300ms 打印一次按键数据。但这需要上位机工具，问同事平时用哪个。

5. 分步操作

每一步都按"目的 → 改哪里 → 怎么验证 → 失败怎么查 → 提交"来写。行号是写讲义时的值，改过代码后会变，以函数名为准。

没有示波器时怎么验证：让芯片自己当裁判 命令时长错了，芯片就不会正确回应。所以芯片的回应本身就能证明时长对不对：
  • 频率校准读回 0x7C–0x84 → 128us 命令和之后的等待都对
  • 读到某个寄存器的出厂默认值 → 39us 命令对
  • 写进去再读回来一致 → 39us 命令和校验位都对
  • 读采样一直不报 CRC 错误 → 5us 命令和之后的等待基本对
示波器的价值在于看"余量"：脉宽是落在误差范围中间，还是贴着边。贴边的话，温度一变、批次一换就可能出问题。所以有条件还是建议量一次。

第 1 步：把时序宏改成按"用途"命名（行为不变）

目的：解决第 3 节说的"TD 编号陷阱"。改完之后，函数里写的是"写寄存器用的时长"，而不是"TD4"，到底对应哪个 TD 由芯片型号决定。这一步芯片型号仍然是 H5，程序行为一点都不变。

改动 1：button.h

在那一大组 #if (2 == USE_HALL_SENSOR) ... #elif ... #endif 结束的 #endif（约第 62 行）后面，加上：

EM_HapticMouse/inc/button.h 
/* 按"用途"命名的时序宏，屏蔽 H5/H6 的 TD 编号差异。
 * 脉冲类（手册写 ±5%）：必须准确，靠实测确认。
 * 等待类（手册写 ">"）：只要求不少于，这里留了余量。 */
#if (6 == USE_HALL_SENSOR)
#define HALL_TD_CONVERT       TD1_DELAY_US      /* 5us ±5%   读采样（HAL_CONVERT） */
#define HALL_TD_CONVERT_WAIT  (DELAY_OUT(8))    /* >4us      读采样后等待 */
#define HALL_TD_WR_REG        TD6_DELAY_US      /* 39us ±5%  读/写寄存器（WR_REG） */
#define HALL_TD_WR_WAIT       (DELAY_OUT(10))   /* >3us      WR_REG 后等待 */
#define HALL_TD_FREQ_CAL      TD10_DELAY_US     /* 128us ±5% 频率校准 */
#define HALL_TD_FREQ_WAIT     (DELAY_OUT(60))   /* >50us     频率校准后等待 */
#else
#define HALL_TD_CONVERT       TD1_DELAY_US
#define HALL_TD_CONVERT_WAIT  TD2_CONTIUNS_DELAY_US
#define HALL_TD_WR_REG        TD4_DELAY_US
#define HALL_TD_WR_WAIT       TD5_DELAY_US
#define HALL_TD_FREQ_CAL      TD7_DELAY_US
#define HALL_TD_FREQ_WAIT     TD10_DELAY_US
#endif

为什么等待类要留余量：CT16B1_DelayUs()（src/Timer.c）的实际延时比参数少 2us 左右，DELAY_OUT(x) 又减了 1，两者叠加后实际延时约为 x−3us，剩下的靠代码本身的执行时间补齐。这个"补齐"从来没被量过。等待类时序只要求"不少于"，多等几微秒没有任何坏处，所以直接给足。

怎么验证（不需要板子）

现在芯片型号仍是 5，新宏展开后和原来一字不差，所以编译出来的 hex 文件应该一个字节都不变。工程里没有用 __DATE__、__TIME__ 这类每次编译都会变的东西，所以这个比较是成立的。

  1. 改代码之前，先在 Keil 里 Rebuild（全部重新编译）一次，把 EM_HapticMouse\output\Sample.hex 复制一份，命名为 before.hex。
  2. 做上面的改动，再 Rebuild 一次。
  3. 在 Windows 命令提示符里进入 output 目录，执行：
fc /b before.hex Sample.hex
通过标准输出"FC: 找不到差异"。

不通过：说明除了宏名还改到了别的东西，对照上表逐行检查。

提交：重构：霍尔时序宏按用途命名，行为不变

uint8_t Hall_osc_calibrate(void)
{
	uint8_t times;

	g_hall_dbg.freq_ok = 0;

	for(times = 0; times < 128; times++)          /* 手册：最多 128 次 */
	{
		/* 手册 V1.7 改版：校准读回期间 SDI 必须为 0。
		 * SSP 读数据的同时会把 tx 发出去，所以 tx 必须全清零 */
		hall_spi_tx[0] = 0;
		hall_spi_tx[1] = 0;
		hall_spi_tx[2] = 0;
		hall_spi_tx[3] = 0;

		g_hall_dbg.freq[1] = hall_spi_rx[3];      /* 左键芯片 */
		g_hall_dbg.freq_times = times + 1;

第 3 步：改写寄存器的校验位，写一个再读回

目的：证明"写"这条路是通的。上一步只证明了"读"。

先理解校验位怎么算

写寄存器时发给每颗芯片的 16 位：

bit15   bit14    bit13 ~ bit8      bit7 ~ bit0
  1     CRCWR    地址 A5~A0        数据 D7~D0

H5：CRCWR = D7^D6^D5^D4^D3^D2^D1^D0              （只算数据）
H6：CRCWR = A5^A4^A3^A2^A1^A0 ^ D7^D6^...^D0     （地址也算进去）

"^"是异或。一串位异或起来，结果就是"1 的个数是奇数还是偶数"，也叫奇偶校验。现有代码有一张表 bit_crc_write_reg[x]：x 里 1 的个数是奇数，就返回 0x40，否则返回 0。0x40 正好是高字节的 bit6，也就是 16 位帧里的 bit14。

H6 要的是"地址和数据合起来的奇偶"，等于"地址的奇偶"异或"数据的奇偶"。所以查两次表再异或一次就够了：

bit_crc_write_reg[data] ^ bit_crc_write_reg[reg & 0x3F]

改动 1：新增写单个寄存器的函数

EM_HapticMouse/app/button.c 
/* 写一个寄存器，链上两颗芯片写同样的值 */
void Hall_WriteReg(uint8_t reg, uint8_t data)
{
	uint8_t j;
	uint8_t head;

#if (6 == USE_HALL_SENSOR)
	/* H6：校验位 = 6 位地址 + 8 位数据的奇偶（手册 §7.4） */
	head = (reg & 0x3F) | 0x80 | (bit_crc_write_reg[data] ^ bit_crc_write_reg[reg & 0x3F]);
#else
	/* H5：校验位只算 8 位数据 */
	head = reg | 0x80 | bit_crc_write_reg[data];
#endif

	for(j = 0; j < 2; j++)
	{
		hall_spi_tx[j * 2 + 0] = head;   /* 高字节：写标志 + 校验位 + 地址 */
		hall_spi_tx[j * 2 + 1] = data;   /* 低字节：数据 */
	}

	Hall_write_register();               /* 移入 4 字节 + 39us 命令 */
}

读回值说明

反向实验：证明校验位真的在起作用

0x30 的二进制是 110000，有两个 1，奇偶为 0。所以就算你忘了把地址算进去，写 0x30 也碰巧能成功。这个测试证明不了地址部分算对了。

做法：把测试里的 0x30 全部换成 0x31（110001，三个 1，奇偶为 1），然后：

  1. 按正确的公式写入 → 应读回 0x21
  2. 临时删掉 ^ bit_crc_write_reg[reg & 0x3F]（相当于退回 H5 的算法），再试 → 应读回 0x20，也就是写入被芯片拒绝
  3. 测完把删掉的那段改回来，测试地址改回 0x30

两个结果都符合预期，才算真正证明了校验位的算法是对的。

思考方式：测试要能"失败" 一个怎么做都会通过的测试，什么也证明不了。设计测试时要问自己：如果我的代码是错的，这个测试会失败吗？用 0x30 测，答案是"不会"，所以要换 0x31，并且故意把代码改错一次，确认测试真的能抓到错误。

现在的设置是"按下时原始值变小"（inc/my_misc.h 约第 41 行，GT_LINA_T1A_H5_PWM 下的 PRESS_KEY_AND_VALUE_INCREASE 为 0）。如果实测按下时数值变大，把它改成 1。方向取决于磁铁朝哪一极对着芯片（手册 §9.10：S 极靠近数值变小，N 极靠近数值变大）。

6.3 增益合不合适

  • "松开"和"按到底"两个值都要离 32 和 16352 有一千左右的距离，留出余量。（这是我给的经验值，不是手册要求）
  • "按到底 − 松开"的差值要远大于静止跳动。代码把全行程分成 100 段（MAX_SEGMENT），差值如果不到跳动的 100 倍，分段值会来回跳。（经验值）
  • 差值不能小于 100，否则代码直接判定无效（my_misc.c 的 Hall_CalculateNode()，约第 301 行）。这是硬性下限。

调增益时四个寄存器必须一起改（手册 §8，0x09、0x0B、0x29、0x2A）：

LNA 增益0x090x0B 高 4 位0x290x2A零点误差
16x0x00（bit5=0）0x80x500x20±500
24x（当前）0x20（bit5=1）0x80x600x28±700
48x0x200x90xA00x40±850
96x0x200xA0xF00x60±1000

0x0B 的低 4 位是 PGA，可以做细调：0x0 = 13.2x 到 0x9 = 24.0x，每档约 +1.2x，当前是 0x5 = 19.2x。先调 PGA，不够再换 LNA 档位。

6.4 依赖数值范围的常量

7. 要问同事的问题

问题要具体到寄存器和数值，对方一句话就能答。

  1. XENO 在 h6_hal_type_mode() 里写了 0x13=0x7F、0x15=0x05、0x16=0x02、0x18=0x03、0x1C=0xFF、0x1E=0x80、0x20=0x80、0x25=0x29，这 8 个地址 V1.9 手册里没有。是必须写的吗？鼠标上两颗芯片需要写吗？
  2. XENO 有偏移校准（h6_offset_cali.c，用到 0x36、0x37）。鼠标上需要做吗？
  3. 16x 增益时，XENO 写的是 0x29=0x4E、0x2A=0x32，手册写的是 0x50、0x20。以哪个为准？
  4. 5us 命令的容差只有 ±0.25us，你们用 GPIO 加定时器这种方式，实测能稳定落在范围内吗？
  5. 这块板子以前用 H5 时，松开和按到底的原始值大概是多少？
  6. 平时用什么上位机工具看 USB 打印的 InfoLog？
思考方式：问问题之前先把功课做完 你第一次找同事时，说的是"把 5528+H6 的项目发我"，但其实你需要的是"H6 的驱动方式和配置"，绕了一圈才对上。好的问题有三个特征：说清楚你要干什么、说清楚你已经查到了什么、问的是对方一句话就能回答的具体点。上面这些问题都是查过手册之后还解决不了的，问出去对方不会觉得被浪费时间。
