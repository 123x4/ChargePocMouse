充电调试第 1 课：充电代码什么时候运行

2026-11-10 · ChargePocMouse / EM_HapticMouse

充电代码挂在程序的两个地方：上电时 Charger_Init() 执行一次，之后主循环每一圈都调用 Charger_PollingTask()，但它每 10 秒才真正干一次活。本课属于固件架构这一层，只回答“什么时候运行”，不看函数内部。

程序结构：超级循环

这个程序没有操作系统，用的是单片机最常见的“超级循环”结构：上电后依次初始化一遍，然后进入 while (1) 死循环，一圈一圈调用各任务函数，永不退出。

充电代码挂在两处：左边初始化里的 Charger_Init()，和主循环里高亮的 Charger_PollingTask()。

初始化：上电只执行一次

Charger_Init() 在 src/device.c 第 434–436 行，排在参数和日志模块初始化之后：

  Param_Init();
	MyDebug_Init();
	Charger_Init();        //charger IC BQ21128

它做四件事：把 PIO0_1 拉低（/CE 低有效，允许充电）、读 0x38 核对芯片型号（应为 0x13：PN=2 即 BQ21128，DEV_REV=3，手册表 6-42，第 58 页）、设置充电电流（表 6-7，第 36 页）、打开充电（EN_CHG，表 6-16，第 42 页）。细节留到第 2 课逐行看。

主循环：每一圈都调用充电任务

while (1) 在 src/device.c 第 507–537 行，每秒转成千上万圈，Charger_PollingTask() 每圈都被调用一次（节选）：

	while (1)
	{
		Device_Scan();        // 读传感器、按键
		Device_Pack();
		Device_Report();      // 把鼠标数据报给电脑
		wwdt_feed();          // 喂单片机自己的看门狗
		PC_Communicate();
		Suspend_Check();
		Ele_PollingTask();
		Task_ParamGuard();
		Charger_PollingTask(); // ← 充电任务
		MyDebug_Task();       // ← 把日志从 USB 发出去
	}

这些任务轮流执行、互相不抢占。前面任何一个任务卡住，后面的（包括充电）都会跟着推迟。

为什么每 10 秒才干一次活

Charger_PollingTask() 的第一行是 POLLING_INTERVAL_MS(CHARGER_POLL_MS);，其中 CHARGER_POLL_MS = 10000。这个宏定义在 inc/my_tick.h 第 15–20 行：

#define POLLING_INTERVAL_MS(x) do{ \
  static uint32_t lastStamp = 0; \
  uint32_t nowStamp = MyTick_GetTickMs(); \
  if(nowStamp - lastStamp < (x)) {return;} \
  lastStamp = nowStamp; \
}while(0)
代码含义
static uint32_t lastStamp记住上次真正执行的时间；static 让它在函数返回后不丢失
MyTick_GetTickMs()上电以来经过的毫秒数
if(现在 - 上次 < x) return;不到 10 秒就直接返回，后面的代码一行不执行
lastStamp = nowStamp;满 10 秒了，更新时间戳，继续往下执行
do{ ... }while(0)让多行宏用起来像一条普通语句，可以安全地跟分号

所以这个函数每一圈都被调用，但绝大多数时候刚进门就出来了，只有每 10 秒真正干一次活。nowStamp - lastStamp 用无符号数相减，毫秒计数约 49.7 天溢出归零时结果仍然正确。

用实测日志验证

2026-11-10 在 G2 板上抓到的日志（未接电池），只保留充电和参数任务的行：

16:54:17.238  [I]Task_ParamGuard: sizeof(AllParam_ts): 189, ...
16:54:17.240  [I]Charger_PollingTask: part 0x13, 0x16=0x81, 0x1E=0x04, 0x1F=0x01
16:54:17.241  [I]Charger_PollingTask: CHG_STAT 0, VBUS_STAT 4, TS_STAT 1
16:54:27.238  [I]Task_ParamGuard: sizeof(AllParam_ts): 189, ...
16:54:27.240  [I]Charger_PollingTask: part 0x13, 0x16=0x81, 0x1E=0x04, 0x1F=0x01
16:54:27.241  [I]Charger_PollingTask: CHG_STAT 0, VBUS_STAT 4, TS_STAT 1
  • 间隔正好 10 秒： 时间戳从 17.24 到 27.24，说明宏在按设计工作。
  • 和 Task_ParamGuard 紧挨着出现： 它也用了 POLLING_INTERVAL_MS(10000)，又在主循环里排在充电任务前面一位。
  • 从没出现 Charger_Init 的行： 它在上电瞬间执行，那时 USB 还没和电脑连上、日志工具也没打开，所以打印丢了。这是周期任务里也打印型号 part 的原因。

这层抽象会在哪里“漏”

  1. 宏里藏着 return。 它看起来像一条普通语句，实际会让整个函数提前返回。所以它只能放在函数第一行，而且只能用在不返回值的 void 函数里。放在函数中间，前半段每圈都跑、后半段 10 秒跑一次，很难查。
  2. “10 秒”不是精确的 10 秒。 只有循环转到这里时才会检查时间。前面某个任务卡住 2 秒，充电任务就晚 2 秒。BQ21128 的看门狗要求 50 秒内喂一次（WATCHDOG 默认 0x1 = 50s，手册表 6-16，第 42 页），现在留了 40 秒余量。超时后寄存器恢复默认值，充电电流还会减半（§6.4.1，第 29 页）。
  3. 开机日志会丢。 日志要等 USB 枚举完成、电脑端工具打开才能收到。上电瞬间的打印（比如 Charger_Init 的型号检查）很可能看不到。想看的信息要放在周期任务里重复打印。
